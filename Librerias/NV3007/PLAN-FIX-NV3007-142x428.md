# Plan de implementación — Adaptación del driver NV3007 a panel Estardyn 142×428

> **Estado:** propuesta, sin implementar
> **Rama sugerida:** `fix/nv3007-142x428`
> **Base:** `libs/NV3007` @ `0f71bf3`
> **Autor del plan:** análisis de `NV3007.c` / `NV3007.h` contra `display/Arduino_NV3007.{h,cpp}`

---

## 1. Contexto

El driver actual es una traducción fiel de `Arduino_NV3007` (Arduino_GFX), cuya secuencia
`nv3007_init_operations` y cuyas constantes de geometría corresponden a un panel **168×428**.
El panel objetivo es un **Estardyn 142×428** con interfaz SPI de 4 hilos.

Los **retardos** de la secuencia (reset, SLPOUT, DISPON, SLPIN) son correctos y **no deben
tocarse**. Los defectos se concentran en geometría, estado inicial del panel y unos pocos
registros dependientes del panel.

### Limitación conocida de este plan

No se dispone del datasheet del NV3007 ni del código de inicialización oficial de Estardyn.
Por tanto:

- Los **offsets de GRAM** se implementan como constantes calibrables, con un valor inicial
  que es una **hipótesis** a validar con el procedimiento de la §8.
- El registro `0xF2` se parametriza, pero su valor correcto para 142 columnas **solo puede
  confirmarse con el init del fabricante**. Ver §7 (riesgos).

## 4. Fase 1 — Geometría y offsets de GRAM (D1, D2, D3)

Es la fase que desbloquea todo lo demás. Sin ella la imagen sale desplazada y recortada.

### 4.1 `NV3007.h` — constantes de geometría

Reemplazar el bloque de `NV3007.h:27-29`:

```c
/* -- Dimensiones visibles del panel -- */
#define NV3007_WIDTH        142U  /**< Ancho visible del panel en píxeles (columnas) */
#define NV3007_HEIGHT       428U  /**< Alto visible del panel en píxeles (filas)     */

/* -- Origen del área visible dentro de la GRAM del controlador --
 *
 * El NV3007 direcciona una GRAM más ancha que el área visible de este panel
 * (142 columnas), por lo que CASET/RASET necesitan un desplazamiento. El valor
 * depende de cómo el fabricante alineó el panel dentro de la GRAM y cambia con
 * la orientación, porque los bits MX/MY/MV de MADCTL remapean el direccionamiento.
 *
 * Los valores por defecto son una HIPÓTESIS (panel centrado horizontalmente en una
 * GRAM de 172 columnas, alineado arriba). Calibrar con el procedimiento descrito en
 * PLAN-FIX-NV3007-142x428.md §8 antes de darlos por buenos. */
#define NV3007_OFFSET_P1_X  15U   /**< Portrait_1  (0°)   - offset X */
#define NV3007_OFFSET_P1_Y   0U   /**< Portrait_1  (0°)   - offset Y */
#define NV3007_OFFSET_P2_X  15U   /**< Portrait_2  (180°) - offset X */
#define NV3007_OFFSET_P2_Y   0U   /**< Portrait_2  (180°) - offset Y */
#define NV3007_OFFSET_L1_X   0U   /**< Landscape_1 (90°)  - offset X */
#define NV3007_OFFSET_L1_Y  15U   /**< Landscape_1 (90°)  - offset Y */
#define NV3007_OFFSET_L2_X   0U   /**< Landscape_2 (270°) - offset X */
#define NV3007_OFFSET_L2_Y  15U   /**< Landscape_2 (270°) - offset Y */
```

> **Nota de diseño.** Se usa una tabla explícita de 4 pares en lugar de derivar los offsets
> de un `GRAM_WIDTH`/`GRAM_HEIGHT` mediante fórmula. La fórmula exigiría saber si el
> controlador refleja (MX/MY) sobre la GRAM completa o sobre el número de líneas activas
> configurado — dato que no tenemos. Ocho constantes calibrables no asumen nada y se
> ajustan en un solo sitio.

### 4.4 `NV3007.c` — aplicar offset en `NV3007_WriteAddrWindow()`

Sustituir el bloque `NV3007.c:628-652`. La caché (`NV3007_CurrentX/Y/W/H`) sigue guardando
coordenadas **lógicas**; el offset se suma solo al emitir los comandos:

```c

        uint16_t xe = x + w - 1U + NV3007_XOffset;
        uint16_t ys = y + NV3007_YOffset;
        uint16_t ye = y + h - 1U + NV3007_YOffset;

        status = NV3007_WriteCommandRaw(NV3007_CMD_CASET);
        status = (status == NV3007_OK) ? NV3007_WriteDataRaw((uint8_t)(xs >> 8)) : status;
        status = (status == NV3007_OK) ? NV3007_WriteDataRaw((uint8_t)(xs & 0xFFU)) : status;
        status = (status == NV3007_OK) ? NV3007_WriteDataRaw((uint8_t)(xe >> 8)) : status;
        status = (status == NV3007_OK) ? NV3007_WriteDataRaw((uint8_t)(xe & 0xFFU)) : status;

        status = (status == NV3007_OK) ? NV3007_WriteCommandRaw(NV3007_CMD_RASET) : status;
        status = (status == NV3007_OK) ? NV3007_WriteDataRaw((uint8_t)(ys >> 8)) : status;
        status = (status == NV3007_OK) ? NV3007_WriteDataRaw((uint8_t)(ys & 0xFFU)) : status;
        status = (status == NV3007_OK) ? NV3007_WriteDataRaw((uint8_t)(ye >> 8)) : status;
        status = (status == NV3007_OK) ? NV3007_WriteDataRaw((uint8_t)(ye & 0xFFU)) : status;

        /* ... resto igual ... */
```

### 4.5 `NV3007.c` — recalcular offsets en `NV3007_Rotate()`

En `NV3007_Rotate()`, tras el `switch` y **después** de que `NV3007_WriteCmdData8()`
devuelva OK, junto a la actualización de `NV3007_Width/Height` (`NV3007.c:708-724`):

```c
    NV3007_XOffset = NV3007_OffsetTable[orientation][0];
    NV3007_YOffset = NV3007_OffsetTable[orientation][1];
```

Añadir además al inicio de `NV3007_Rotate()` una validación del parámetro, porque ahora
indexa una tabla:

```c
    if ((unsigned)orientation > (unsigned)NV3007_Orientation_Landscape_2)
    {
        return NV3007_INVALID_PARAM;
    }
```

> El `default:` del `switch` deja de ser el camino para valores fuera de rango; se convierte
> en el caso `Portrait_1`. La invalidación de la caché (`NV3007.c:721-724`) ya existente es
> **imprescindible** aquí, porque el offset acaba de cambiar.

### 4.6 `NV3007.c` — implementar `NV3007_SetOffset()`

```c
NV3007_Status_t NV3007_SetOffset(uint16_t x_offset, uint16_t y_offset)
{
    if (!NV3007_Initialized)
    {
        return NV3007_NOT_INITIALIZED;
    }

    NV3007_XOffset = x_offset;
    NV3007_YOffset = y_offset;

    /* Forzar reenvío de la ventana con los nuevos offsets */
    NV3007_CurrentX = 0xFFFFU;
    NV3007_CurrentY = 0xFFFFU;
    NV3007_CurrentW = 0U;
    NV3007_CurrentH = 0U;

    return NV3007_OK;
}
```

## 5. Fase 2 — MADCTL en la inicialización (D4)

`nv3007_init_operations` no contiene el comando `0x36`. En Arduino_GFX eso lo cubría
`Arduino_TFT::begin()` llamando a `setRotation()`; el port en C perdió ese paso, así que
el panel arranca con el MADCTL por defecto del reset (orientación y orden RGB/BGR
indefinidos).

En `NV3007_Init()`, reemplazar el bloque `NV3007.c:564-576`:

```c
    NV3007_CurrentX = 0xFFFFU;
    NV3007_CurrentY = 0xFFFFU;
    NV3007_CurrentW = 0U;
    NV3007_CurrentH = 0U;
    NV3007_Width    = NV3007_WIDTH;
    NV3007_Height   = NV3007_HEIGHT;

    /* NV3007_Rotate() y NV3007_InvertDisplay() exigen el módulo inicializado; se marca
     * antes y se revierte si alguna de las dos falla, para no dejar el driver medio
     * configurado y reportando NV3007_OK a futuras llamadas. */
    NV3007_Initialized = 1U;

    /* La secuencia de init del fabricante no incluye MADCTL (0x36): sin esto el panel
     * quedaría con la orientación y el orden de color por defecto del reset. */
    status = NV3007_Rotate(NV3007_Orientation_Portrait_1);
    if (status != NV3007_OK) { NV3007_Initialized = 0U; return status; }

    status = NV3007_InvertDisplay(false);
    if (status != NV3007_OK) { NV3007_Initialized = 0U; return status; }

    return NV3007_OK;
```

> **Comprobar en la calibración:** si el panel es IPS, los colores saldrán invertidos con
> `NV3007_InvertDisplay(false)`. El equivalente al flag `_ips` de Arduino_GFX
> (`Arduino_NV3007.cpp:80`) es cambiar esta llamada a `true`. Se resuelve con el Test F (§8).

## 6. Fase 3 — Encendido y apagado del panel (D5, D6, D7, D8)

Reemplazar `NV3007.c:741-763` completo:

```c
/**
 * @brief Enciende la pantalla: sale del modo Sleep y activa la salida de display.
 *
 * @return NV3007_Status_t Estado de la operación.
 */
NV3007_Status_t NV3007_DisplayOn(void)
{
    NV3007_Status_t status = NV3007_SendCommand(NV3007_CMD_SLPOUT);
    if (status != NV3007_OK) { return status; }

    HAL_Delay(NV3007_SLPOUT_DELAY);

    return NV3007_SendCommand(NV3007_CMD_DISPON);
}

/**
 * @brief Apaga la pantalla: desactiva la salida de display y entra en modo Sleep.
 *
 * @details DISPOFF antes de SLPIN evita el destello que produce cortar la alimentación
 *          del panel con la salida de display todavía activa.
 *
 * @return NV3007_Status_t Estado de la operación.
 */
NV3007_Status_t NV3007_DisplayOff(void)
{
    NV3007_Status_t status = NV3007_SendCommand(NV3007_CMD_DISPOFF);
    if (status != NV3007_OK) { return status; }

    status = NV3007_SendCommand(NV3007_CMD_SLPIN);
    if (status != NV3007_OK) { return status; }

    HAL_Delay(NV3007_SLPIN_DELAY);

    return NV3007_OK;
}
```

Esto resuelve D5 (falta DISPOFF), D6 (falta DISPON), D7 (`NV3007_CMD_DISPOFF` pasa a usarse)
y D8 (el status deja de ignorarse).

> `NV3007_DeInit()` (`NV3007.c:593`) llama a `NV3007_DisplayOff()` y sigue siendo correcto
> con la nueva implementación: ahora apaga el display además de dormir el controlador.

## 7. Fase 4 — Registros dependientes del panel (D9)

### 7.1 Parametrizar `0xF2`

`0xF2` con `{0x26, 0x1B, 0x0B, 0x20}` es el candidato principal a cambiar: en la secuencia
alternativa `nv3007_279_init_operations` del mismo repo
(`display/Arduino_NV3007.h:297`) el primer byte pasa a `0x2C`, lo que indica que ese campo
escala con la geometría/porch del panel.

En `NV3007.h`, junto a los retardos:

```c
/* -- Registros dependientes del panel --
 *
 * 0xF2 controla el timing horizontal y su primer byte escala con la geometría del panel
 * (0x26 en el init de 168 columnas de Arduino_GFX, 0x2C en la variante de 279).
 * Si Estardyn proporciona su fichero de inicialización, sustituir por sus valores. */
#ifndef NV3007_REG_F2_BYTES
#define NV3007_REG_F2_BYTES  { 0x26U, 0x1BU, 0x0BU, 0x20U }
#endif
```

En `NV3007_RunInitSequence()`, reemplazar `NV3007.c:322-326`:

```c
    {
        static const uint8_t f2[4] = NV3007_REG_F2_BYTES;
        uint8_t k;

        st = (st == NV3007_OK) ? NV3007_WriteCommandRaw(0xF2) : st;
        for (k = 0U; (k < 4U) && (st == NV3007_OK); k++)
        {
            st = NV3007_WriteDataRaw(f2[k]);
        }
    }
```

### 7.2 Documentar el bloque dependiente del panel

Añadir un comentario de bloque al inicio de `NV3007_RunInitSequence()` (`NV3007.c:194`)
listando qué registros son específicos del panel y por tanto candidatos a sustituir si
Estardyn entrega su init:

| Rango | Función (inferida) | ¿Depende del panel? |
|---|---|---|
| `0x9A`–`0x9E`, `0x8F`, `0x83`–`0x85` | Booster / VGH / VGL / oscilador | Sí |
| `0x60`–`0x7F` | Curvas gamma (positiva y negativa) | Sí |
| `0x50`–`0x56` | VCOM y control de fuente | Sí |
| `0xA0`–`0xD1`, `0xB0`–`0xBF` | Señales GIP (gate-in-panel) | Sí — depende de nº de gates (428, igual) |
| `0xE0`–`0xF1` | Formas de onda STV/CLK del gate driver | Sí — 428 líneas, probablemente reutilizable |
| `0xF2` | Timing horizontal / porch | **Sí — depende de nº de columnas (142 ≠ 168)** |
| `0x35`, `0x44`, `0x46` | Tearing effect y scanline | No |
| `0x3A` = `0x05` | Formato de píxel RGB565 (16 bpp) | No — coincide con los 2 B/píxel del driver |

**Conclusión operativa:** al compartir las 428 líneas con el panel de referencia, el timing
vertical es previsiblemente reutilizable. El riesgo se concentra en `0xF2` y, en menor
medida, en los bloques de potencia y gamma (que afectan a brillo/color, no a geometría).

## 10. Plan de verificación

Ejecutar en orden. Cada test asume el anterior superado.

### Test A — Arranque y color plano
`NV3007_Init()` → `NV3007_FillScreen(NV3007_COLOR_RED)`.
✅ Toda la superficie roja, sin bandas negras en los bordes.
❌ Banda muerta en un lado → offset X o Y incorrecto. Ir al Test C.

### Test B — Marco de 1 píxel (validación de offsets)

❌ Falta un lado o hay hueco → ajustar con `NV3007_SetOffset()` en incrementos de 1 hasta
que encaje; anotar el valor.

### Test C — Calibración de las 4 orientaciones
Para cada valor de `NV3007_Orientation_t`: `NV3007_Rotate(o)` → repetir Test B →
ajustar con `NV3007_SetOffset()` → anotar el par (x, y).
Trasladar los 8 números finales a `NV3007_OFFSET_*` en `NV3007.h` y **repetir el test sin
`NV3007_SetOffset()`** para confirmar que la tabla es correcta.

### Test D — Esquinas exactas
```c
NV3007_DrawFilledRectangle(0, 0, 1, 1, NV3007_COLOR_GREEN);
```

✅ Dos píxeles verdes en esquinas opuestas del panel físico.

### Test E — Orden de color e inversión
Tres bandas horizontales rojo / verde / azul con `NV3007_DrawFilledRectangle()`.
✅ Los colores coinciden con los nombres.
❌ Rojo y azul intercambiados → falta `MADCTL_BGR` (bit `0x08`, no definido en `NV3007.h`;
añadirlo si hace falta).
❌ Colores en negativo → cambiar la llamada de la Fase 2 a `NV3007_InvertDisplay(true)`
(panel IPS).

### Test F — Ciclo de sueño
`NV3007_DisplayOff()` → 2 s → `NV3007_DisplayOn()` → `NV3007_FillScreen(...)`.
✅ El panel se apaga sin destello y vuelve mostrando el contenido correcto.

### Test G — Regresión de primitivas
Círculo, círculo relleno, triángulo relleno, `RoundRect` y `DrawBitmap` cerca de los cuatro
bordes.

## 12. Riesgos y puntos abiertos

| Riesgo | Impacto | Mitigación |
|---|---|---|
| Los offsets por defecto (15, 0) son una hipótesis | La imagen sale desplazada en el primer arranque | `NV3007_SetOffset()` permite calibrar sin recompilar (Test C) |
| `0xF2` incorrecto para 142 columnas | Artefactos de barrido, *tearing*, parpadeo — **no** desplazamiento | Solo se resuelve con el init de Estardyn; el resto del plan es independiente |
| Los bloques de potencia/gamma son de otro panel | Brillo, gamma o contraste subóptimos | No bloquea el funcionamiento; ajustar si el init del fabricante llega |
| El panel refleja MX/MY sobre la GRAM completa o sobre las líneas activas | Offsets asimétricos entre orientaciones | La tabla de 4 pares no asume nada: cada orientación se calibra por separado |
| Falta `MADCTL_BGR` en `NV3007.h` | Rojo/azul intercambiados si el panel es BGR | Test E lo detecta; añadir `#define NV3007_MADCTL_BGR 0x08U` |

**Lo que este plan NO resuelve:** confirmar bit a bit los registros propietarios de la
secuencia de inicialización. Eso requiere el datasheet del NV3007 o el fichero de
inicialización de Estardyn, y es el único punto donde el plan depende de información externa.
